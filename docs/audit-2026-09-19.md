# Verification audit — 19 September 2026

Two repositories, audited against `docs/MASTER_IMPLEMENTATION_SPEC.md`.

| Repo | Language | Visibility | Role |
|---|---|---|---|
| `Anwarito-lbd/agri-edge` | Python | private | edge runtime, ops backend, models, mechanical |
| `Anwarito-lbd/agri-edge-web` | TypeScript / Next.js | private | operations station UI, phone companion |

This is **not** the Phase 0 inventory — `docs/repo-audit.md` already lists what
exists. This audit asks a different question: *does it do what the repository
says it does?* Every finding below came from running something, not from
reading a status table.

That distinction found four defects, three of them in checks that were
reporting success without executing.

---

## Summary

| | |
|---|---|
| Suite before | **16 failing**, 758 passing |
| Suite after | **1128 passing**, 5 skipped |
| Findings | 13 (12 fixed, 1 open) |
| Safety-architecture violations | **0** |

The architecture holds up. Rules 1–4 of the spec — AI never reaches a motor,
the flight controller owns flight control, payload safety is independent of AI,
third parties sit behind adapters — are all respected, and in the case of Rule 1
they are respected by *absence*: there is no code anywhere in `src/` that can
drive a PWM output, a servo, a pump or a valve. That is the right way for it to
be true at this stage.

What is weaker is the machinery meant to catch regressions. Three of the four
most serious findings are cases where a check existed, appeared to pass, and was
not running -- and they chain: the BOM made a dependency guard fail as a parse
error, which hid that the suite was red; `make lint` exited 0 without a linter,
so ruff had never run; when it finally ran it found nine broken HTTP routes,
including the approval gate the spec requires before any application.

## Findings

### A1 — `connect()` returned True with no aircraft **[FIXED]**

**Severity: high (latent).** The most serious thing in either repository.

`vehicle/ardupilot.py` imported `agri_edge.mavlink.connection` and
`agri_edge.mavlink.telemetry`. Neither module has ever existed — the real
reader is `agri_edge.telemetry.mavlink_link.MavlinkTelemetry`. Both imports sat
inside a bare `except Exception`, so the `ModuleNotFoundError` was swallowed,
execution fell through to the simulated branch, and `connect()` returned `True`
regardless.

Reproduced against a dead UDP port:

```
connect() -> True
source = simulated | connected = True | lat/lon = 45.0 -75.0
```

No aircraft, no autopilot, no radio — and a plausible position in Ontario.

The flag was the smaller half of the problem. The coordinates were the larger
one: anything consuming that state would georeference detections against a
fabricated origin, and the spec's own default failure policy (§35, *uncertain
position → application OFF*) would never fire, because the position did not
look uncertain.

**Why it is only latent:** `VehicleState` is currently consumed by tests alone.
Nothing in the pipeline reads it yet. It would have become live the moment
someone wired the adapter in — which is the next step on the priority list.

**Fixed** in `fix(vehicle): connect() must report whether a vehicle is there`:

* the import names the module that exists, and an `ImportError` is logged
  rather than absorbed;
* `connect()` returns whether a **real link** was established — simulation
  remains available and is no longer disguised as a connection;
* a simulated state carries `lat=None, lon=None, alt_m=None`. No position at
  all beats a convincing wrong one;
* `VehicleState` gains `simulated`, separate from `sitl`. A SITL flight is real
  MAVLink from a simulated vehicle; an adapter inventing numbers because it
  could not connect is a different thing, and one flag cannot mean both;
* six tests pin the corrected contract, including one that walks the module's
  AST and imports every `agri_edge.*` it names — a dead import inside a bare
  `except` is invisible any other way.

### A2 — 24 files carried a UTF-8 BOM; 16 tests failed because of it **[FIXED]**

**Severity: high.** The suite was red on `master`.

`ast.parse` raises `SyntaxError` on a string beginning with U+FEFF, so
`tests/test_runtime_deps.py` — the guard that keeps heavy imports off the Pi —
failed with a parse error on sixteen modules at once. The modules were fine.
The first three bytes were not.

The source is PowerShell: `Set-Content`, `Out-File` and `>` write UTF-8 *with* a
BOM by default on Windows. It is invisible in an editor and in `git diff`.

It also silently breaks anything that reads a file as text and parses it: JSON
and YAML loaders, several linters, and the shebang of a shell script — the
kernel sees three bytes before `#!`, so the script runs under the wrong
interpreter or not at all. `scripts/` was affected.

**Fixed**, plus `tests/test_source_encoding.py` (327 checks) asserting no BOM in
any tracked text file, every `.sh` still starting with its shebang, and every
Python file parsing.

### A3 — `make lint` passes when the linter is absent **[FIXED]**

**Severity: medium.** Same failure mode as A2: a check that looks like it ran.

```make
lint:
	@command -v ruff >/dev/null 2>&1 && ruff check src tests || echo "ruff not installed — skip"
```

Exit code 0 either way. Nothing distinguishes "clean" from "never ran".

This is notable because the repository elsewhere gets this exactly right — the
CI `extras` job greps its own output and fails if the MAVLink tests *skipped*,
with the comment *"a skip here is indistinguishable from a pass in the summary
line, so assert the count instead of trusting the tick."* The Makefile does not
hold itself to that standard.

**Fixed.** `lint`, `format` and `typecheck` now fail when their tool is
missing, `bootstrap` installs them, and a `[tool.ruff]` section selects rules
that catch bugs rather than reformat the tree — `F`, `E4/E7/E9`, `B`, `PLE` and
a few security rules. The style families are off: 127 of the first 356 findings
were `Optional[x]` versus `x | None`, and burying a real undefined-name under
127 of those is how a lint gate gets switched off.

**Its first run found A10.**

### A4 — CI does not lint, format-check, typecheck, or build the frontend **[PARTLY FIXED]**

**Severity: medium.** Spec §11 requires format check → lint → static analysis →
unit → integration → frontend build → container build. `.github/workflows/test.yml`
runs tests only.

The test job itself is well designed — a 3.11/3.12 matrix, the dependency
boundary checked first and alone, and the extras job described above. The gap is
breadth, not quality.

**Partly fixed.** A `static` job now runs `make lint` and `make build`, with
`ruff format --check` and `mypy` advisory until the tree is annotated. The
frontend build stays open — it belongs in `agri-edge-web`, which has no CI at
all (A9).

### A5 — `make` is not installed on the development machine **[MITIGATED]**

**Severity: medium.** `make bootstrap|lint|test|build` — the spec's §76
acceptance commands — cannot be run here at all. CI does not use the Makefile
either, so `make lint` and `make build` are verified nowhere.

**Mitigated:** the new `static` CI job invokes `make lint` and `make build`
rather than calling the tools directly, so the targets a developer types are the
ones CI proves work. Installing `make` locally is still worth doing.

### A6 — Missing `make` targets from spec §10 **[FIXED]**

`typecheck`, `test-integration`, `sitl`, `hailo-smoke`, `edge-run` were absent,
plus `format` and `clean`. All added, wired to the scripts that already exist.

### A7 — No `.env.example` **[FIXED]**

**Severity: low, but §47 requires it.** No secrets are committed — a scan across
`src/`, `scripts/`, `config/`, `ground_iot/`, `training/` and `workstation/`
found none, and credentials correctly come from the environment in
`store/farmos.py` and `telemetry/ntrip.py`. What is missing is the file that
*documents* which variables exist: `FARMOS_USERNAME`, `FARMOS_PASSWORD`,
`FARMOS_CLIENT_SECRET`, `NTRIP_USERNAME`, `NTRIP_PASSWORD`.

**Fixed.** `.env.example` written, and `.gitignore` extended — it did not
previously cover `.env` at all, which would have mattered the moment someone
created one.

### A8 — 14 MB of archives committed alongside their own contents **[FIXED]**

**Severity: low, permanent.**

```
7.9 MB  mechanical/handoff/airframe_renders_improved.tar.gz
6.4 MB  mechanical/handoff_pack.tgz
2.0 MB  mechanical/handoff/renders/airframe_top.png     (also inside the archive)
...
```

The archives duplicate files committed uncompressed next to them, and git
stores both forever. Renders regenerate in about 18 seconds from
`mechanical/blender_airframe.py`. Spec §74 warns against exactly this.

**Fixed.** Checked rather than assumed first: 22 files across the two archives,
none of them absent from `git ls-files`. Nothing was lost. `*.tgz` and
`*.tar.gz` are now ignored.

This shrinks the working tree, not the history — that needs a rewrite, which is
worth doing before the repo is shared more widely and not before.

### A9 — `agri-edge-web` has no tests and no CI **[FIXED]**

**Severity: medium.** 14.8 MB, Next.js, TypeScript, 5 dependencies, with real
API routes — `/api/v1/command/[...path]`, `/api/v1/alerts/[id]/ack`,
`/api/v1/stream`. `package.json` defines `dev`, `build`, `start`, `lint`. There
is no test directory and no `.github/`.

**Correction to the first draft of this audit:** `/api/v1/command/[...path]` is
not a command proxy. It is a deliberate reject surface — all five verbs return
403 and name what they forbid. That was already right.

The route that actually forwarded was `/api/ops/[...path]`, and it forwarded
*everything* on GET and POST with no authentication, no session and no
middleware anywhere in the app — including `POST /api/ops/vra/approve`, the
human-in-the-loop gate that authorises a variable-rate prescription. Anyone who
could reach the Next server could approve one, and the upstream audit record
would name whatever `actor` string they sent. Spec §150 (roles) and §152
(deliberate confirmation) were both unmet at that seam.

**Fixed:**

* `src/lib/ops-proxy-policy.ts` — reads forward; writes are allowlisted and off
  unless `OPS_ALLOW_WRITES=1`; paths that look like vehicle commands are refused
  on every method and cannot be enabled by configuration; traversal is rejected
  before the encoding is relied on. This is not authentication — it is the
  smaller honest thing: the proxy stops handing out authority nobody asked it
  to hand out. Real roles belong upstream, next to the audit log.
* 28 tests calling the real handlers, pinning the refusals that were already
  right as well as the new policy, and asserting the proxy does not reach
  upstream at all for a blocked write.
* CI: test, typecheck, lint, build — with the build pointed at a dead
  `OPS_API_URL`, so a page that fetches at build time instead of request time
  fails the build.


### A10 — Nine POST routes stranded inside `do_GET` **[FIXED]**

**Severity: high.** Found by A3's linter on its first run, which is the whole
argument for A3 being treated as a real finding rather than housekeeping.

The block beginning at `/api/ops/vra/approve` had been pasted into `do_GET`,
where the local name `body` is never bound. Against a live server:

```
POST /api/ops/vra/approve  -> 404   (do_POST never had the route)
GET  /api/ops/vra/approve  -> 500   NameError: name 'body' is not defined
```

`/api/ops/vra/approve` is the human-in-the-loop gate. Spec §39 and §105 both
require an operator to approve a variable-rate prescription before it reaches a
mission, and §151 requires that approval to be audited. None of it could happen,
because the endpoint could not be called — on either verb.

Also unreachable, from the same block: the mapping workflow
(create/validate/approve/execute, §112) and the camera event, scout report,
manual observation and mobile note ingestion (§142–144).

**Why no test caught it.** The ops suite calls `approve_prescription()`
directly, and that function works and is covered. What was untested was whether
the HTTP layer could reach it. A route table has to be tested through the door
it is served behind.

**Fixed**, with 18 tests that speak HTTP, including a static one that walks
`OpsHandler`'s AST and fails any method reading `body` without binding it.


### A11 — CI had been red for four commits, and not because a test failed **[FIXED]**

**Severity: high.** Discovered while pushing the fixes above.

`tests/test_provenance.py` imported `torch` and `tests/test_webodm.py` imported
`PIL` at module level, so pytest failed at **collection**. The summary reports
that as an error, not as a missing optional extra, and both files pass on this
machine because it carries torch and Pillow from the training work. That gap
between the dev machine and the runner is why red CI went unexamined.

`training/export_onnx.py` now imports torch inside `main()`. `DATASET_PROVENANCE`
and `build_meta` are pure metadata helpers — the record of what a model was
trained on — and demanding an 800 MB training stack to read them was never
right. The provenance tests now *run* in CI rather than skipping.

The first fix was verified with `pytest --collect-only` under a fake import
blocker, and **that check was wrong twice over**:

* `--collect-only` cannot see an import inside a fixture, and
  `tests/test_data_prep.py` had one — collection passed, every test errored at
  setup, CI stayed red;
* the blocker raised from `find_spec`, which a genuinely missing module never
  does (it returns `None`), so a test guarded with
  `importlib.util.find_spec("PIL") is not None` blew up under the fake and
  would have passed on a real runner.

Replaced with `make test-lean` (`scripts/lean_runner_check.py`): a throwaway
venv holding `pip install -e .` and pytest, nothing else, then the whole suite.
It immediately found two more things — `test_integration.py` skipped on a
missing model but not a missing Pillow, and `test_source_encoding.py` scanned
the throwaway venv's site-packages, growing the suite from 1128 tests to 3665.
More tests from a scope bug is not more coverage.

Clean core-only venv: **1094 passed, 21 skipped, exit 0.**

### A12 — `make hailo-smoke` could not be exercised at all **[FIXED]**

**Severity: low.** `scripts/hailo_compile.sh` needs the Hailo Dataflow
Compiler, which is x86_64 Linux only and therefore WSL2 on this machine — and
WSL2 is not installed. So the script could not be run, even to check its
argument handling.

Added `--dry-run`: every preflight check runs and the compile command is
printed rather than issued. The script is now known-good *before* the one
machine that can run it exists. Verified: preflight passes, arch resolves, 823
calibration images found.


### A13 — Both shell scripts were unrunnable on Linux **[FIXED]**

**Severity: high.** Found on 20 September, the moment WSL2 existed and the
Hailo preflight was run for the first time on the platform it targets.

```
scripts/hailo_compile.sh: line 17: $'': command not found
scripts/hailo_compile.sh: line 18: set: pipefail: invalid option name
```

`core.autocrlf=true` is the Windows default and there was no `.gitattributes`,
so every checkout rewrote LF to CRLF in the working tree. bash takes the
carriage return as part of the last token on each line, so `set -euo pipefail`
became `pipefail<CR>` and every path argument gained an invisible character.
Nothing in the error names line endings.

It survived because **the scripts had never been run on Linux** — and everything
they exist for (the Hailo Dataflow Compiler, ArduPilot SITL) needs a machine
this project did not have until Stage 0 was done. `make hailo-smoke` had been
exercised only on Windows, through Git Bash, which tolerates CRLF.

This is the third member of the same family, after the BOM (A2) and the CRLF's
own cousin in CI: **bytes that are invisible in an editor and fatal on the
machine the file is meant to run on.**

**Fixed:** `.gitattributes` pins LF for everything Linux-bound and CRLF for the
one thing that is not (`*.ps1`); binaries are marked `binary`, because a text
conversion silently corrupts a `.onnx` or `.hef` and it then fails at load with
an error about anything but line endings. Two guards added — no CRLF in any
shell script, and `.gitattributes` actually containing the rule. The first
catches a bad file; the second catches the missing rule that would let every
future file be bad on a Windows clone.

Verified afterwards in WSL2: preflight passes for `hailo8l`, `hailo8` and
`hailo10h`.

## What was verified as sound

* **Rule 1 — AI never drives motors.** No PWM, servo, RC-override, nozzle, pump
  or valve code path exists in `src/`. The only occurrences of those words are
  in comments explaining why they are absent.
* **Rule 2 — the flight controller owns flight control.** No attitude loop, no
  mixing, no failsafe logic in Python.
* **Rule 3 — payload safety independent of AI.** `may_drive_treatment` requires
  `validated_locally AND in_treatment_zone is True`, and fails closed on both.
* **Rule 4 — adapters.** `pymavlink` appears only inside
  `vehicle/ardupilot.py` and `telemetry/mavlink_link.py`. No autopilot type
  escapes into application code.
* **The read-only MAVLink contract.** `MavlinkTelemetry` has no method that
  could write to a vehicle, and a test asserts it. Rewiring the adapter onto it
  (A1) did not open a door — a test now asserts that too.
* **RTK corrections bypass the autopilot** and go to the GNSS receiver's own
  serial port, preserving the read-only contract rather than making an
  exception to it.
* **Credentials** come from the environment, never from config.
* **`docs/status.md` does not overclaim.** Spot-checked against the code:
  Hailo live inference is marked `❌ BLOCKED`, the physical actuator `❌`
  throughout, `validated_locally` false. The spec's §61 rule — no misleading
  green checkmarks — is being followed.
